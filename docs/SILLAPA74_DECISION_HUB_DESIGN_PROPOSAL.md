# Sillapa 74 — Decision & Participation Hub (Design Proposal)

**สถานะ:** PROPOSED / ยังไม่อนุมัติให้พัฒนา Backend, เปิดระบบจริง หรือย้ายข้อมูล  
**ข้อมูลจากผู้จัด ณ:** 14 ตุลาคม 2569  
**Repository:** `infobwd/sillapa` (หน้าเว็บข้อมูล Public)  
**ระบบธุรกรรมหลัก:** `infobwd/AcademicCompetitionManager` (การรับสมัคร/ทีม/ผลแข่งขัน/สิทธิ์ผู้ใช้)

## 1. วิสัยทัศน์

เปลี่ยนหน้าเว็บผลการแข่งขันครั้งที่ 73 และร่างแผนครั้งที่ 74 จากการเป็นข้อมูลย้อนหลังแบบ Static เป็น **ศูนย์ข้อมูลประกอบการตัดสินใจสำหรับผู้จัด** และ **ศูนย์ข้อมูลเตรียมแข่งขันของโรงเรียน/ครู** โดยไม่สร้างระบบรับสมัครและฐานข้อมูลคะแนนซ้ำกับระบบหลัก

**ข้อควรจำ:** ข้อมูลใน `index.html` เป็น snapshot; `localStorage` ของเครื่องผู้ใช้ไม่ใช่ฐานข้อมูลส่วนกลาง; จำนวนทีม/ผลแข่งขันจริงครั้งที่ 74 ยังไม่ได้เชื่อม Backend ณ ขณะออกแบบ

## 3. Persona และคำถามหลัก

### A. ผู้จัดการแข่งขัน (ส่วนกลาง/เขตและกลุ่มเครือข่าย)

**คำถามที่เว็บต้องตอบได้**

1. กิจกรรมใดเปิดแข่งขันจริงแยกตามระดับกลุ่ม/เขต และมีนโยบายตัวแทนกี่ทีมต่อรายการ? กิจกรรมใดเปิดสมัครเขตโดยตรง?
2. มีกี่กลุ่มที่ **ส่งแล้ว / ส่งไม่ครบ / ส่งแล้วรอตรวจ / ผ่านตรวจ / ถูกส่งกลับแก้ไข** เทียบกับกำหนด 4 ธ.ค.?
3. รายการใดจำนวนทีมมาก, น้อย, เป็นศูนย์จริง หรือ **ยังไม่ได้รับข้อมูล**? (ห้ามรวม “ศูนย์” กับ “ไม่มีรายงาน”)
4. แต่ละกิจกรรมคาดต้องใช้ห้อง สถานที่ วัน ช่วงเวลา กรรมการ และทรัพยากรเท่าไร? มีจุดชนกันหรือไม่?
5. กรรมการคนใดเคยตัดสินรายการเดิม แต่ปีนี้เป็นผู้ควบคุมทีม/มีโรงเรียนส่งแข่งขัน/ติดภารกิจซ้อน?
6. ข้อมูลรายการแข่งขัน จำนวนทีม และผลต่างครั้งที่ 73–74 เชื่อถือได้เพียงใด? มาจากชุดไหนและอัปเดตเมื่อใด?

**Dashboard เสนอ:** กล่องตัวชี้วัด “กลุ่มส่งตัวแทนแล้ว”, “รอรับรอง”, “รายการเปิดแข่ง”, “ทีมรอการแข่งขันระดับเขต”, “รายการที่ต้องหาสนาม/กรรมการ”, แผนภูมิแยกกลุ่ม/หมวด/ระดับชั้น, ตารางรายการความเสี่ยงที่เจาะถึงกิจกรรมได้, ตัวกรอง stage/cluster/activity/status, CSV/PDF สรุปประชุมแบบไม่เผย PII

**ข้อสำคัญ:** KPI ต้องผูกนิยาม denominator, สถานะการนำส่ง, เวอร์ชันข้อมูล และเวลาปรับปรุง ห้ามนับ “แผน” เป็น “ทีมสมัครจริง” หรือ “ส่งแล้ว” เป็น “รับรองแล้ว”

### B. โรงเรียน/ครูผู้ส่งแข่งขัน

**คำถามที่เว็บต้องตอบได้**

1. โรงเรียนของฉันเคยลงแข่งรายการใด ได้คะแนน/เหรียญ/เป็นตัวแทนในครั้งที่ 73?
2. รายการครั้งที่ 74 **เปิดจริงหรือยังเป็นร่าง**; ชั้นเรียน/จำนวนเด็ก/ครู/เกณฑ์ที่ประกาศตรงกับความพร้อมหรือไม่?
3. โรงเรียนมีทีม **วางแผน / สมัครจริง / ผ่านตรวจ / เป็นตัวแทนกลุ่ม / ได้สิทธิ์เขต / แข่งแล้ว** อะไรบ้าง?
4. ต้องทำอะไรและส่งให้ใครภายในช่วงใด? แจ้งเตือนเฉพาะขั้นตอนที่ต้องทำ (อย่าถือวันส่งผลตัวแทนเป็น deadline สมัครของทุกทีม)
5. ถ้ากิจกรรมถูกปิด เปลี่ยนชื่อหรือเกณฑ์ มีรายการทางเลือกใดที่เป็นกิจกรรมเปิดจริง?
6. มีวัน/เวลา/สถานที่ของกิจกรรมที่ **ประกาศยืนยันแล้ว** หรือยัง?

**หน้าโรงเรียนของฉัน:** ค้นหาและเลือกโรงเรียน (Public = ข้อมูลภาพรวม), เมื่อยืนยันตัวตนให้ดูข้อมูลทีมของโรงเรียนเดียว, สรุป checklist และ timeline, ย้อนผลเดิม, เปิดกติกาต้นฉบับ, สถานะการสมัคร, รายการสิ่งที่ต้องแก้ไข, แผนกิจกรรมที่ต้องสรุปส่ง และดาวน์โหลดแบบตรวจสอบ

## 4. ตำแหน่งระบบและ Source of Truth

```text
[AcademicCompetitionManager PHP/MySQL]
  canonical activities, stage policy, cluster/school/team/entry,
  representative-promotion, verified results, venue, judges (authorized)
                       |
          approved read-only API / sanitized export
                       v
[infobwd/sillapa — GitHub Pages / Decision Hub]
  public results and statistics 73, official 74 activity catalogue,
  published schedule, approved public aggregates, source timestamp
                       |
             personalized, authenticated deep links
                       v
[AcademicCompetitionManager]
  private school records, registration changes, member PII,
  representative approval, score write, admin/audit operations
```

- ใช้ `cycle_id`, `activity_id`, `school_id`, `cluster_id`, `stage_scope` เป็นคีย์อ้างอิงหลัก ห้ามจับคู่ข้อมูลจริงด้วยชื่อกิจกรรม/ชื่อโรงเรียนอย่างเดียว
- Dashboard นี้ห้ามเขียนตรงลงฐานข้อมูลการแข่งขันและห้ามสร้างตารางรายชื่อครู/นักเรียนคู่ขนาน
- **Public endpoint** ส่งเพียงชุดข้อมูลสรุปที่ได้รับอนุญาต ไม่ส่งเบอร์โทร วันเกิด หมายเลขประชาชน รายชื่อทีมที่ยังไม่อนุมัติ/ข้อมูลติดต่อกรรมการ
- **Private endpoint** ต้องใช้การยืนยันตัวตนและตรวจสิทธิ์ฝั่ง Server ที่ระบบหลัก ไม่ใช่เพียงซ่อนปุ่มในหน้า Public
- เก็บสถานะการเผยแพร่ `draft / under_review / confirmed / published / superseded`, เวอร์ชันข้อมูล, ที่มา, ผู้รับรอง, เวลาอัปเดต และการแยก proposed/confirmed ของกำหนดการ
- กำหนดค่า cache/privacy และ fallback ข้อมูลเก่าให้ชัดเจน เมื่อ API ใช้งานไม่ได้แสดงสถานะ “ข้อมูล ณ …” ไม่ใช้คำว่า “สด/ปัจจุบัน”

## 5. สองระดับและนโยบายที่ยืดหยุ่น

รองรับ **Cluster → District** โดยนโยบายต่อกิจกรรมมีได้หลายแบบ: `representative_only`, `open`, `representative_plus_open`, `closed`. จำนวนตัวแทนต่อกิจกรรม/กลุ่มอาจมากกว่า 1 ทีมตาม policy ที่อนุมัติ

**Flow แนะนำสำหรับส่งผลตัวแทนระดับกลุ่ม:** คัดเลือกผู้มีสิทธิ์ → ยืนยันทีม/เอกสาร/ครู/นักเรียนตามเกณฑ์ → กลุ่มกดส่ง → เขตตรวจสอบ → รับรองหรือส่งกลับแก้ → ล็อกรอบส่งเมื่ออนุมัติ → ออก snapshot ที่มีลายทางข้อมูลและเวลาตรวจสอบ

**Status mapping (ข้อเสนอ ไม่ใช่ของที่ใช้งานอยู่แล้ว):** `not_started / drafting / submitted / needs_revision / verified / locked` พร้อม `submitted_at`, `verified_at`, `submitted_by`, `approved_by` และเหตุผลเมื่อถูกส่งกลับ

**หลักการนับ:** รายการเขตที่เปิด `open` ไม่ควรถูกนับว่ากลุ่มส่งผลตัวแทนไม่ครบ; กิจกรรม `representative_plus_open` ต้องแยกทีมจากกลุ่มกับทีมที่สมัครตรงและลดการนับซ้ำ

## 7. Acceptance Criteria สำหรับการออกแบบครั้งถัดไป

- หน้า Public แยก **ข้อมูลปีที่แล้ว, ร่างปีนี้, ข้อมูลยืนยันแล้ว, ข้อมูลยังไม่รับ/รอยืนยัน** อย่างมองเห็นได้ชัด
- วันส่งผลตัวแทน **4 ธ.ค. 2569** อยู่บนหน้าเว็บ พร้อมระบุว่าเป็นกำหนดส่งระดับกลุ่ม ไม่ใช่วันแข่งขัน
- ช่วงเขต **21–24 ธ.ค. 2569** มีป้าย `ประมาณการ` และไม่สร้างตารางกิจกรรมที่ยังไม่มี
- ระบบรองรับ policy เปิดรับสมัครตรงระดับเขตและหลายตัวแทนต่อกิจกรรม โดยไม่สรุปผิดว่าแต่ละกลุ่มต้องมีทีมทุกกิจกรรม
- ผู้จัดต้องเจาะจาก KPI ถึงรายกลุ่ม/กิจกรรม และเห็น `as_of` ของข้อมูลได้
- ผู้ใช้แบบไม่ล็อกอินไม่เห็น PII ของครู นักเรียน และผู้เกี่ยวข้องจากข้อมูลธุรกรรม
- ผู้ใช้โรงเรียน ก ไม่สามารถอ่านหรือเปลี่ยนข้อมูลส่วนตัวของโรงเรียน ข ผ่าน API ได้
- หากยังไม่มี Backend: ห้ามระบุว่าแผนครูหรือสถานะทีมมีการซิงก์หรือรับรองจากเขต
- มีขั้นตอนทดสอบ Local-First และอนุมัติแยกสำหรับ Merge, Staging และ Production ตาม `infobwd/repo-governance`
